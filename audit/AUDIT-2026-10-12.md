Объект: исходники commit b8c656b. Рабочие исходники не изменены. В этой копии нет cookies.json, рабочего лога и базы: фактический ответ Яндекса не проверен. Аудит включает статический разбор Python, UI и локальные воспроизведения на временной SQLite/искусственных ZIP. Полный интеграционный тест с аккаунтом не проводился.

## Ошибка prepare FAIL

`unlim_worker.py:157–176` вызывает внутренний web-метод `mpfs/bulk-download-prepare` через `/models-v2`, ожидая `download_url` строго на верхнем уровне JSON. Любой HTTP 200 без этого поля превращается в None без записи причины. HTTP != 200 и исключения логируются в `logs/unlim_worker.log`, но UI получает только общий FAIL.

Возможные причины, пока не подтвержденные: истекшая сессия/CSRF sk, прикладная ошибка при HTTP 200, изменение структуры ответа или контракта запроса, недействительные resource IDs, ограничения размера архива, ограничение частоты, отказ именно bulk-операции. Номер batch — счетчик попыток, а не устойчивый идентификатор группы файлов. Повторяющиеся номера после перезапуска не доказывают обработку разных групп.

Запрет массового скачивания из предоставленного лога не следует. Официальная справка по-прежнему описывает скачивание из безлимита через Яндекс Диск 3.0 и копирование фото в обычную папку. Это не гарантирует работоспособность недокументированного bulk API:
https://yandex.ru/support/yandex-360/customers/disk/web/ru/media-upload.html?lang=ru

Дополнение пользователя: сейчас выбор нескольких файлов не скачивается также через сайт Яндекс.Диска; раньше работал. Это свидетельство проблемы групповой выгрузки вне скрипта, но оно не устанавливает глобальный запрет, его причины или состояние одиночного скачивания. Связь с атаками на дата-центры не подтверждена. Приоритет следующей проверки — скачивание одного оригинала; при успехе отдельный single-file транспорт, а не bulk с одним элементом.

## Порядок восстановления скачивания

1. Остановить повторяющиеся попытки. Сохранить состояние перед миграциями: согласованная резервная копия SQLite, а не копирование только .db во время записи WAL. Не сбрасывать всю БД.
2. Сделать диагностику prepare: HTTP-код, Content-Type, безопасный код прикладной ошибки, имена полей JSON, число и суммарный объем файлов, длительность. Не писать cookies, sk, полный ответ или подписанные URL в лог. Различать auth, rate-limit, schema, invalid-item, archive-limit, network.
3. Проверить в браузере одну фотографию и группу из 2–3. Сопоставить метод, payload и форму ответа текущего клиента с кодом. Если сессия устарела — обновить ее; если изменился контракт — поправить только подтвержденные поля.
4. Выполнить ограниченную пробу одним воркером: сначала 1 файл, затем 2–3, затем 10. Текущий `--batch 1` все равно вызывает bulk-download-prepare и НЕ является независимым пофайловым скачиванием. Не оставлять текущий воркер на бесконечных повторах при провале пробы.
5. Если проблема зависит от размера пачки — ограничивать ее и числом файлов, и байтами, делить только соответствующие ошибки. Один недоступный объект изолировать, не блокируя остальные. Auth и rate-limit не лечить дроблением/параллельностью.
6. Если bulk-метод действительно недоступен, реализовать отдельный single-file режим по подтвержденному запросу скачивания оригинала в текущем клиенте. Не подменять оригинал preview и не выдумывать новый endpoint. Проверить отдельные фото и видео, размеры и хэши.
7. Если рабочий web-контракт получить нельзя, использовать официально описанный экспорт через приложение Яндекс Диск. Другой вариант — копирование в обычную папку и REST-загрузка, с учетом квоты обычного хранилища; это отдельная операция с облаком, автоматически не выполнялась.
8. До массовой выгрузки исправить пофайловое подтверждение, коллизии и атомарную запись. Для ранее помеченных downloaded безлимитных файлов провести отдельную сверку: их текущий статус не доказывает полноту копии, local_path воркер не заполняет.

## Рекомендуемая архитектура

Общий диспетчер очереди и проверок + два транспорта: официальный REST и адаптер web/photoslice. Результат транспорта должен быть структурированным (код, retryable, retry_after, идентификатор ресурса), а не URL либо None. Единый манифест связывает remote ID, метаданные, local_path и проверенную локальную копию. Успех определяется проверкой файла; успех всего задания — полнотой сканирования и отсутствием незавершенных обязательных объектов.

## Проверки

`python3 audit/reproduce_unlim.py` — четыре локальных воспроизведения на исходных функциях, извлеченных AST без выполнения инициализации модулей:

- HTTP 200 с JSON error теряется без диагностики.
- Возвращенная в pending пачка немедленно выбирается повторно.
- Один распакованный файл помечает скачанными два запрошенных ID (исполнена настоящая ветка main).
- Другой файл с тем же именем и размером молча пропускается.

Все четыре сценария подтверждены. Проверен синтаксический разбор всех корневых Python-файлов. Скрипт не использует сеть, секреты или рабочую БД. Он воспроизводит дефекты текущей версии, а не утверждает корректность приложения; после исправлений его следует заменить регрессионными тестами ожидаемого поведения.
